Beli

Food Rating App

Consumer App Feature Redesign UX Research

Problem

Beli's rating page overwhelmed users with too many choices at once, and the absence of menu search forced them to recall dish names from memory, turning a simple task into a frustrating, high-effort experience.

Team

Solo

Role

UX/UI Designer

Duration

Jan – Mar 2025

Product

Beli is a food rating and restaurant tracking app. I redesigned the rating page and introduced menu search with autofill to make logging reviews faster, with less memory burden and fewer unnecessary choices.

Goal

Redesign Beli's rating experience so users can log specific dishes faster, with less recall burden and fewer redundant steps.

Responsibilities

UX Research • User Interviews • Problem Definition • Sketching • Wireframing • Prototyping

research define ideation sketches solution impact reflection

01 Research: User Interviews

Users forget dish names, skip features they don't understand, and use notes to fill the gaps.

To validate whether this friction was widespread, I surveyed five Beli users aged 18–30. Three clear patterns emerged that shaped every design decision that followed.

User Finding

4 out of 5 users

forget the name of their menu item at least 50% of the time when rating a restaurant.

Most Commonly Used Features

  1. Add photos
  2. Add notes
  3. Who did you go with?

Least Commonly Used Feature

Add favorite dishes

with 80% of users stating they either never or rarely use it, reporting that it was redundant or that they did not have a single favorite dish to add.

"I never understood why Beli put the 'Add Photos' option at the bottom of the screen. It's the feature I use the most, and it's hard to find."— Beli User
"Sometimes you just don't have one favorite dish, and other times you may have many, so I usually just include all of my options in the notes section."— Beli User

02 Define

The real problem: a disconnect between how users think and how the app works.

Users didn't log reviews the way the app expected. They forgot dish names, skipped features like Favorite Dishes and Tags, and instead wrote everything in Notes to avoid extra steps. This wasn't a feature gap, it was a mismatch between the app's mental model and the user's actual post-meal behavior.

These findings shaped two core objectives:

  • Enhancing Menu Search — How can we implement a system that lets users find and log dishes without relying on recall?
  • Streamlining the Rating Experience — How can we reorganize the rating screen to reduce cognitive overload and make the review process feel fast, not tedious?

03 Ideation

Decision matrix: finding the right approach to menu discovery.

I narrowed the menu search problem to three possible approaches and evaluated each against the key user need: helping users find dish names with the least amount of friction and effort.

Approach ✓ Strengths ✗ Weaknesses
Autofill /
Suggestion Bar
  • Helps find menu items given a small keyword
  • Seamlessly adds items into the notes field
  • Familiar from iMessage and other apps
  • Multiple items may start with the same word
  • Won't help if user can't remember any keywords
  • May autofill words unrelated to the menu item
Menu Search
  • Browse the full menu without remembering names
  • Keyword search also available
  • Categories make items easy to find
  • More taps: search → scroll → click on item
  • Must repeat the process for each item added
@ Symbol to
Trigger Search
  • Signals intent to autofill a menu item
  • Familiar from @-mentioning on other platforms
  • May confuse users who want to type the symbol literally
  • Users may not discover it activates search

I decided to combine autofill and menu search. If users remember part of a dish, autofill helps them find it instantly. If they don't remember anything, they can browse the full menu by category. Together, these features make finding dishes easy without introducing a new interaction pattern.

These were the key design decisions I made to address the problems I encountered during my research process:

Insight

Most users forget menu item names when writing a review after leaving the restaurant, increasing drop-off rate.

→

Design Decision

Add menu search and autofill so users can browse or type a keyword to find dishes so no recall is required.

Insight

Users already rely on Notes to log dishes, thoughts, and context, making it the primary way they review restaurants.

→

Design Decision

Made Notes the primary focus of the review flow, giving it greater visibility while allowing selected menu items to be added directly.

Insight

"Add Photos" is the most-used feature but is buried at the bottom of the rating page. Users had to scroll past other options to reach it.

→

Design Decision

Move photo-adding to the top of the rating screen so that we match placement to actual usage patterns.

Insight

The rating page showed too many options at once, adding cognitive load without adding value, many features (like "Add Favorite Dish") end up not being used.

→

Design Decision

Remove "Add Favorite Dishes" and use progressive disclosure to break the review process into manageable steps.

04 Sketches

Sketching menu search, autofill, and a restructured rating page.

Before building anything, I sketched out the three changes in parallel to see how they'd interact: menu search needed to fit the existing rating flow, autofill needed to feel native to the notes field, and the rating page itself needed to lose visual weight without losing useful functionality.

From these sketches, I created a mid-fidelity mockup that places "Add Photos" prominently at the top, matching the most-used feature to the highest-visibility position.

To avoid feature overload on the rating page, I used progressive disclosure to break the review process into sequential steps so each screen asks the user to do one thing at a time.

05 Solution

Restructured Rating Page

What changed and why it mattered:

  • Photos moved to the top — highest-used feature now in the highest-visibility position
  • Progressive disclosure breaks the review into steps, reducing the number of decisions on any one screen
  • Autofill suggestions appear as you type in notes — fast dish logging without leaving the field

Menu Search

What changed and why it mattered:

  • Direct menu access from the rating page — no need to leave the review flow
  • Browse the full menu by category when you can't recall a name
  • Tap to add a dish straight to your notes — selected items populate instantly, no typing required

06 Possible Impact

Metrics I would test to measure success.

If these features shipped, the questions I'd want to answer are whether the changes actually reduced the friction users reported and whether the new features got used.

Review speed

Average time to complete a review from open to submit

Dish logging

Autofill adoption

Menu search usage

Perceived ease

User-rated difficulty of completing a review (post-task survey)

07 Reflection

What I Learned.

This project taught me how much friction can hide in a seemingly small interaction. The core problem (forgetting a dish name) sounds minor, but it exposed a deeper misunderstanding between how the app was structured and how people actually behave after a meal. Fixing it required translating that behavioral insight into a concrete system change, not just a UI adjustment.

As a next step, I would rethink the home page to better separate personal ratings from restaurant discovery. My research showed that users rarely engaged with Beli's Featured Lists, raising a bigger question: why aren't people using Beli for recommendations? Do they trust competitors like Google Maps more, or are they primarily using Beli to see where their friends are eating? Answering this would help clarify Beli's core value and guide future product decisions.
